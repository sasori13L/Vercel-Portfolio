# Workspace Access Demo

A standalone Next.js App Router app using React, TypeScript, and Tailwind CSS to demonstrate organization-level access control with Supabase Auth and PostgreSQL Row Level Security (RLS). It lives outside the portfolio app so its build and Vercel project can be managed independently.

## Local app setup

Requirements: Node.js 20.9+ and npm.

```sh
cd demos/workspace-access
npm install
cp .env.example .env.local
npm run dev
```

The app provides email/password sign-in, organization membership loading, and task management. Its root page is a Next.js Client Component because it uses interactive Supabase browser authentication. The only intended browser configuration is the Supabase project URL and anon/publishable key shown in `.env.example`; `NEXT_PUBLIC_` values are public and must never contain a service-role key.

## Supabase schema and sample data

1. Create a Supabase project for this demo. For CLI deployment, install the Supabase CLI, run `supabase link --project-ref <project-ref>` from this directory, then run `supabase db push`. Alternatively, apply the SQL in `supabase/migrations/` using the SQL Editor.
2. In **Authentication → Users**, create two email/password users for reviewers. Disable public sign-up if it is not needed. Set passwords outside this repository and share them through an appropriate private channel.
3. Copy each user's UUID from the Auth user list.
4. Open `supabase/seed-demo-data.sql`, replace `<USER_A_AUTH_UUID>` and `<USER_B_AUTH_UUID>` with the matching user UUIDs, and run the script in the Supabase SQL Editor as a trusted project administrator. User A is a member of Northstar Studio; User B is a member of Cedar Works. The SQL creates fictional sample tasks and stable task IDs for later isolation checks.
5. Add the Supabase project URL and anon/publishable key to the local `.env.local` file. These values are public client configuration; database grants and RLS policies provide the access boundary.

Membership rows are intentionally absent from migrations because Auth user IDs are generated by the Supabase project. Do not create or alter memberships from the browser. Do not put the service-role key in local browser configuration or Vercel client environment variables.

## Database access contract

The initial migration creates `organizations`, `memberships`, and `tasks`, adds the specified foreign keys, defaults, task status constraint and indexes, then enables RLS on every table. Authenticated users can read only organizations and memberships connected to their own user ID. Task select, insert, update, and delete have separate policies. Inserts require membership in the target organization and `created_by = auth.uid()`; updates check both the existing and resulting row.

Table grants further restrict access: `anon` receives no table privileges, memberships are read-only to authenticated clients, and task clients may insert only the organization/title/description/status columns and update only title/description/status. This prevents a browser request from changing `organization_id` or `created_by`, even for a task the user can otherwise edit. No public membership write policy is defined.

The app loads membership and organization rows with the signed-in Supabase client. Task queries are scoped to the selected organization for clarity, while RLS remains the database authorization boundary. New task writes derive their organization from the active membership, omit `created_by` so the database default supplies the session identity, and show neutral errors if a request is denied.

All sample content is fictional. The demo users can change task data in their own organizations once CRUD is implemented. Do not store sensitive data in this project.

## Vercel setup

Create a separate Vercel project connected to this repository and set its **Root Directory** to `demos/workspace-access`. Choose the Next.js framework preset, or let Vercel detect it; Vercel supplies the Next.js build and output defaults. Add `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` as environment variables for each deployment environment. Do not add `SUPABASE_SERVICE_ROLE_KEY`.

## Limitations

This is a focused RLS demonstration, not a security audit or production task-management system. Reviewer accounts and sample tasks are mutable demo data. Keep the Supabase project limited to synthetic content and review the policies whenever the schema or browser operations change.
